Hands-on tutorial

A three-node Kubernetes cluster, built from code

This page replays what we actually did: create three virtual machines with Terraform, configure them with Ansible, start a k3s cluster, and manage it from a web UI. Every step shows the command you run, which tool it starts, and which file does the work.

  • 3 small VMs (1 CPU, 1 GB each)
  • 2 tools: Terraform and Ansible
  • 1 command per step: make …
  • 0 manual logins to set anything up

Ideas

The big picture

Doing this by hand means clicking in a cloud console, logging in to each machine and typing commands. It works once and you can never repeat it exactly. Here every step is written down as code, so you can delete everything and get the same cluster back. That is called infrastructure as code, and it is the point of the project.

Terraform

What should exist

You describe machines in .tf files. Terraform asks the cloud’s API to create them and remembers what it made in a state file.

Ansible

How it is set up

You describe the setup in YAML. Ansible logs in over SSH and makes each machine match, skipping whatever is already right.

Kubernetes

What is running

You say “run 3 copies of this app”. Kubernetes keeps that true and restarts copies elsewhere if a machine dies.

Words you will meet

Provider
The plugin that lets Terraform talk to one cloud’s API.
State
Terraform’s memory of what it created. Lose it and Terraform forgets your machines.
Plan / Apply
Plan previews changes and creates nothing. Apply performs them and costs money.
Drift
Reality no longer matches the code, for example someone changed something by hand.
Inventory
The list of machines and groups Ansible manages. Terraform generates it here.
Role / Playbook
A role is a reusable bundle of tasks. A playbook says which roles run on which machines.
Idempotent
Running it again changes nothing if everything is already right.
Dry run
Ansible’s --check: shows what would change without changing it.
Control plane / agent
The cluster’s brain, and the workers that run your containers.
Join token
A secret the server creates so agents can prove they may join.
A rule to keep

If it is about a machine existing, it is Terraform. If it is about what is inside a machine, it is Ansible. If it is about what runs on the cluster, it is Kubernetes (the k8s/ folder).

Ideas

Before you start

Three things must exist before any code runs.

  1. An API token from your cloud provider, saved in a file called .env in the repo. Git ignores that file, so the token never reaches a repository.
    .env
    GCX_API_URL='https://api.example-cloud.com/api'
GCX_API_TOKEN='your-token-here'

    Keep the single quotes: a token can contain characters such as | that a shell would otherwise treat as an operator.

  2. An SSH key pair made just for this project. The private key stays on your machine, the public key is copied to every VM.
    terminal
    ssh-keygen -t ed25519 -N '' -C 'homelab-lab' -f ~/.ssh/homelab
  3. Docker and Terraform installed. Docker runs Ansible in a container, so Ansible itself needs no install.

Prove the connection works before you build anything. This is a single curl call, with no Terraform or Ansible involved:

terminal
make check-api
expected
GCX API /projects: HTTP 200

200 means the URL and token work. 401 means a bad token.

How the token reaches Terraform

the path of the token
.env  ──(Makefile)──▶  TF_VAR_gcx_api_token  ──▶  var.gcx_api_token
                                                  └─▶ providers.tf:  Authorization: "Bearer <token>"

Terraform turns any environment variable named TF_VAR_name into the variable name. The Makefile reads .env and exports those variables for you.

Step 1 Terraform

Create the machines

Terraform has no built-in knowledge of any cloud. A provider plugin translates “create a VM” into that cloud’s API calls. The cloud used here has no dedicated provider, so the generic restapi provider sends plain HTTP requests instead.

Three files to read first

terraform/envs/prod/providers.tf how to reach the API
providers.tf
provider "restapi" {
  uri = var.gcx_api_url                       # the API address

  headers = {
    Authorization  = "Bearer ${var.gcx_api_token}"   # who you are
    Accept         = "application/json"
    "Content-Type" = "application/json"
  }

  id_attribute         = "data/slug"          # where an object's ID sits in a reply
  write_returns_object = true
}

Every API reply here looks like {"status": "...", "data": {...}}, so the ID is found at data/slug.

terraform/modules/vm/main.tf the request for one VM

A module is a reusable block. This one is called once per VM. It describes the exact request sent to the API.

modules/vm/main.tf (abridged)
resource "restapi_object" "vm" {
  path = "/virtual-machines"                  # create = POST /virtual-machines

  data = jsonencode({                         # the JSON body of that request
    name     = var.name
    template = var.template                   # which operating system
    plan     = var.plan                       # 1 CPU / 1 GB / 35 GB
    is_public = true                          # give it a public IP
    networks  = var.network == "" ? [] : [var.network]
    user_data = "#cloud-config\nssh_authorized_keys:\n  - ${var.ssh_public_key}\n"
  })

  id_attribute = "data/slug"
  read_path    = "/virtual-machines/{id}"     # 'make plan' re-reads the VM here

  destroy_method = "POST"                     # this cloud deletes by 'cancel request'
  destroy_path   = "/billing/service-cancel-requests/{id}"
}
  • data is the request body. Each field answers a question the API asks: name, operating system, size, public IP, network.
  • user_data is a cloud-init script. On first boot the VM runs it and installs your public key, so you can log in without a password.
  • read_path is how Terraform checks the VM still looks right. make plan calls it.
  • destroy_* describes deletion. This cloud has no DELETE for VMs, so it is another POST.
terraform/envs/prod/main.tf which VMs exist

Covered in chapter 5: it creates the server first, then the agents inside the server’s network.

Run it

  1. Preview. Read it. A plan creates nothing.
    terminal
    make plan
    expected
    Plan: 5 to add, 0 to change, 0 to destroy.
  2. Apply. Terraform repeats the plan and waits for you to type yes. This is the step that costs money.
    terminal
    make infra
  3. Check. Three views must agree: your code, Terraform’s state, and the real cloud.
    terminal
    make status      # what the cloud says: Running / Starting / Error
make plan        # must say: No changes
    make status
    NAME    STATE    PUBLIC_IP
k3s-01  Running  103.78.129.175
k3s-03  Running  103.78.129.174
k3s-02  Running  103.78.129.173
What happens inside make infra

For each VM Terraform sends POST /virtual-machines with the JSON above, reads the ID from the reply, and saves it in terraform.tfstate. Next time, make plan compares your code with that file and with the real cloud, and shows only the difference. That is why “No changes” is meaningful.

Step 2 Terraform → Ansible

The hand-over: Terraform writes the host list

Ansible needs to know which machines exist. Nobody types an IP address by hand: Terraform fills in a template and writes the file Ansible reads.

The template

terraform/envs/prod/inventory.tftpl has blanks such as ${ansible_user} and a loop over the machines.

The resource that fills it

local_file "inventory" in main.tf renders the template and writes ansible/inventories/prod/hosts.yml.

Where the IP comes from

The VM module reads it from the API reply and exposes it as the output public_ip.

ansible/inventories/prod/hosts.yml (generated, never edit by hand)
all:
  vars:
    ansible_user: ubuntu                              # who Ansible logs in as
    common_admin_ssh_public_key: "ssh-ed25519 ..."    # key the baseline gives the admin user
    ansible_ssh_private_key_file: /run/keys/homelab   # path INSIDE the container
  children:
    k3s_server:
      hosts:
        k3s-01: { ansible_host: 103.78.129.175 }
    k3s_agent:
      hosts:
        k3s-02: { ansible_host: 103.78.129.173 }
        k3s-03: { ansible_host: 103.78.129.174 }

k3s_server and k3s_agent are groups. Playbooks use them to say “run this on the server only” or “run this on the agents only”.

The IP can be empty right after creation

A VM may not have an address yet when Terraform writes the file. When the VMs are Running, run make infra once more. It only refreshes the file.

Step 3 Ansible

Ansible in a container

Ansible runs inside a Docker container so that you, a teammate and later a pipeline all use exactly the same version. Nothing is installed on your machine and nothing special is installed on the VMs. They only need SSH and Python, which Ubuntu already has.

Makefile: the command every Ansible target reuses
docker run --rm -t \
  -v "$(CURDIR):/work" \                          # the repo appears at /work
  -v "$(SSH_KEY):/run/keys/homelab:ro" \          # your private key, read-only
  -e ANSIBLE_CONFIG=/work/ansible/ansible.cfg \
  homelab-ansible  ...
  • --rm deletes the container when the command ends. That is why you never see it in docker ps. The image stays.
  • The key is mounted read-only and never copied into the image, so it cannot leak with the image.
  • ansible.cfg sets StrictHostKeyChecking=accept-new: trust a host the first time, refuse it if its key later changes.
  1. Build the image once, or after you change the Dockerfile.
    terminal
    make ansible-build
  2. Check that Ansible can log in to every machine.
    terminal
    make ping
    expected
    k3s-01 | SUCCESS => ... ping: pong
k3s-02 | SUCCESS => ... ping: pong
k3s-03 | SUCCESS => ... ping: pong

Ansible’s ping is not a network ping. It logs in over SSH, runs a tiny Python check and answers pong. If it works, Ansible can control the machine.

Step 4 Ansible

The baseline role

Fresh machines are open and unconfigured. The common role gives every machine the same safe starting point. The entry point is ansible/playbooks/site.yml, and the tasks are in ansible/roles/common/tasks/main.yml.

AreaWhat it does on the VMWhy
PackagesInstalls ufw, fail2ban, chrony, curl, ca-certificatesThe tools the rest of the role needs
Admin userCreates devops with your key and passwordless sudoAn account you control, not the image default
SSH hardeningNo root login, no passwords, 3 attemptsPassword guessing on port 22 is the most common attack
SwapCreates and enables a 1 GB swap fileA 1 GB machine can freeze without it
FirewallDeny incoming, allow outgoing, allow port 22 and the private networksClosed by default
fail2banBlocks IPs that keep failing SSH loginsAutomatic defence
chronyKeeps the clock accurateKubernetes and TLS need correct time

Run it, then run it again

terminal
make check       # dry run: shows what WOULD change
make config      # the real run
make config      # again: must say changed=0
first run
k3s-01 : ok=31 changed=5  failed=0
k3s-02 : ok=25 changed=3  failed=0
second run
k3s-01 : ok=…  changed=0  failed=0
k3s-02 : ok=…  changed=0  failed=0

The second run showing changed=0 proves the role is idempotent: the machines now match the code.

Four patterns worth learning from this role

Desired state

state: present means “make sure it exists”. It does nothing if it already does.

creates:

A command task is skipped if the named file exists. This makes one-off commands safe to repeat.

changed_when

Tells Ansible whether a command really changed something, so the recap is honest.

Check-mode tolerance

ignore_errors: "{{ ansible_check_mode }}" lets a task fail only during a dry run, when a new user or package does not exist yet.

Why the firewall tasks are in this order
roles/common/tasks/main.yml
- name: Allow configured ports          # 1. allow SSH first
  community.general.ufw: { rule: allow, port: "22", proto: tcp }
- name: Allow traffic from trusted networks   # 2. nodes trust each other
  ...
- name: Default deny incoming           # 3. then close everything else
  community.general.ufw: { default: deny, direction: incoming }
- name: Enable the firewall             # 4. switch it on LAST
  community.general.ufw: { state: enabled }

If the firewall were switched on before port 22 was allowed, Ansible would cut off its own connection and lock itself out.

Why the SSH config is tested before it is applied

The hardening file is followed by a task that runs sshd -t. If the configuration had a typo, the task fails before the SSH service reloads, so you are never locked out by a bad file. The reload itself is a handler: it runs once at the end, and only if the file really changed.

Step 5 Terraform

Three nodes, one private network

For a cluster, the nodes must reach each other privately. The cloud makes a new private network for each VM unless you tell it which one to join. So Terraform creates the server first, reads which network it landed in, and only then creates the agents inside that same network.

terraform/envs/prod/main.tf (abridged)
locals {
  vms = {
    "k3s-01" = { role = "server" }              # add a line to add a node
    "k3s-02" = { role = "agent" }
    "k3s-03" = { role = "agent" }
  }
}

module "vm_server" { ... for_each = local.servers ... }

resource "time_sleep" "server_ready" {
  create_duration = "60s"
  depends_on      = [module.vm_server]
}

data "restapi_object" "server_vm" {              # read-only lookup
  path         = "/virtual-machines"
  search_key   = "name"
  search_value = local.server_name
  depends_on   = [time_sleep.server_ready]
}

module "vm_agent" {
  ...
  network         = local.server_network         # join the server's network
  require_network = true                         # refuse to build without one
}
A safety check that paid off

require_network = true adds a precondition in the module: if the network slug is empty, Terraform refuses to create the agent instead of silently making a separate network. On the first attempt the lookup read the wrong level of the API reply, the check fired, and nothing wrong was built.

Step 6 Ansible Kubernetes

The cluster

k3s is a small, complete Kubernetes. It ships its own container engine, containerd, so Docker is not installed on the nodes. A Docker daemon on a 1 GB machine would only waste memory.

One playbook, four plays, in order

PlayRuns onRoleResult
1allcommonBaseline everywhere
2k3s_serverk3s_serverControl plane installed; join token created
3k3s_agentk3s_agentWorkers join using that token
4k3s_servera taskWaits until every node is Ready
roles/k3s_agent/tasks/main.yml how an agent joins
k3s_agent tasks (abridged)
- name: Install the k3s agent and join the cluster
  ansible.builtin.command:
    cmd: /usr/local/bin/k3s-install.sh
    creates: /usr/local/bin/k3s-agent-uninstall.sh      # run once only
  environment:
    INSTALL_K3S_VERSION: "{{ k3s_version }}"            # pinned version
    INSTALL_K3S_EXEC: "agent --node-ip {{ ansible_facts['default_ipv4']['address'] }}"
    K3S_URL:   "https://{{ hostvars[groups['k3s_server'][0]]['ansible_facts']['default_ipv4']['address'] }}:6443"
    K3S_TOKEN: "{{ hostvars[groups['k3s_server'][0]]['k3s_server_node_token'] }}"
  no_log: true                                          # keep the secret out of the output

hostvars[...] is how a task running on one machine reads a value that was created on another. Here an agent reads the token that the server made.

Why the server runs no applications

The server is tainted (CriticalAddonsOnly), so only system pods run on it. With about 1 GB of RAM it needs all of it for the control plane, and your applications land on the two agents.

Why the firewall rule uses the machines’ own network facts
inventories/prod/group_vars/all/vars.yml
common_ufw_allow_from_cidrs:
  - "{{ ansible_facts['default_ipv4']['network'] }}/{{ ansible_facts['default_ipv4']['prefix'] }}"
  - "{{ k3s_pod_cidr }}"          # 10.42.0.0/16  pods
  - "{{ k3s_service_cidr }}"      # 10.43.0.0/16  services

The nodes trust their own private subnet, the pod network and the service network on every port. Traffic from the internet still reaches only the ports in the allow list. Computing the subnet from each node’s facts means no address is hard-coded.

Run it and look at the cluster

terminal
make config      # runs all four plays; waits until every node is Ready
make nodes       # kubectl get nodes -o wide
make nodes
NAME     STATUS  ROLES          AGE    VERSION        INTERNAL-IP
k3s-01   Ready   control-plane  3m29s  v1.37.2+k3s1   10.0.0.231
k3s-02   Ready   <none>         2m42s  v1.37.2+k3s1   10.0.0.41
k3s-03   Ready   <none>         2m42s  v1.37.2+k3s1   10.0.0.185

Step 7 Ansible Kubernetes

Deploy applications and use the UI

Kubernetes objects live as YAML files in k8s/. Applying them puts them in the cluster.

k8s/headlamp/helmchart.yaml (abridged)
apiVersion: helm.cattle.io/v1
kind: HelmChart                       # k3s has a built-in Helm controller
metadata: { name: headlamp, namespace: kube-system }
spec:
  repo: https://kubernetes-sigs.github.io/headlamp/
  chart: headlamp
  version: 0.46.0                     # pinned on purpose
  targetNamespace: headlamp
  createNamespace: true

A HelmChart object tells k3s to download and install a chart, so no Helm program is needed on any machine.

What make deploy does

  1. Creates /opt/k8s on the server.
  2. Copies the whole k8s/ folder there.
  3. Runs k3s kubectl apply -R -f /opt/k8s.

It goes through Ansible and SSH, which is already open. Running kubectl from a laptop instead would need the Kubernetes API port (6443) open to the internet.

Open the UI without opening a port

terminal
make headlamp-token   # prints a login token, valid 8 hours. Treat it like a password.
make headlamp         # keep it running, then open http://localhost:8080

Headlamp lets you browse every resource, read logs, open a shell in a pod, and create or edit anything from YAML. It does not have a click-through deploy wizard like Portainer. You write or paste YAML, which is how Kubernetes is really used.

Deleting a file does not delete the object

kubectl apply only adds and changes. To remove something, delete it explicitly (make kubectl ARGS="delete namespace NAME"), delete /opt/k8s/NAME on the server, and delete the folder from k8s/. Otherwise the next make deploy brings it back.

What went wrong, and what it taught

Every one of these happened while building this. Errors from a cloud API usually name the exact field or object at fault, so read the message first. A rejected request creates nothing, so most of these cost nothing.

500 when creating an SSH key
Cause
The provider’s key endpoint failed for every input.
Fix
Install the key with cloud-init user_data instead.
Lesson
Have a second route when one feature is broken.
422 “network_plan field is required”
Cause
A required field was missing from the request body.
Fix
Look the value up with a read-only API call and add it.
Lesson
A rejected request creates nothing, so errors are cheap.
403 “delete_public_ip field is required”
Cause
The delete request lacked a field that is not in the published docs.
Fix
Added the field to destroy_data.
Lesson
The delete request is saved in the state when the resource is created, so a code fix only helps new resources. For older ones, delete through the API and then run terraform state rm.
Resource precondition failed (network slug empty)
Cause
The lookup read the wrong level of the reply: .networks instead of .data.networks.
Fix
Corrected the path in server_network.
Lesson
The safety check stopped agents from being built in the wrong network.
“Insufficient address capacity”
Cause
Two VMs asked for a public IP at the same instant.
Fix
Created the failed VM again on its own.
Lesson
Cloud APIs can race. Create things one at a time when they compete for a limited resource.
REMOTE HOST IDENTIFICATION HAS CHANGED
Cause
A rebuilt VM got an IP that an earlier VM had used, but with a new SSH host key.
Fix
ssh-keygen -R <ip> -f ansible/.ansible/known_hosts
Lesson
This warning protects you. Understand why the key changed before you clear it.
Ansible dry run fails on a task
Cause
A dry run does not create things, so a later task cannot find the new user, file or package.
Fix
ignore_errors: "{{ ansible_check_mode }}" on those tasks only.
Lesson
In a real run the same task is still a real failure.
ansible-lint var-naming
Cause
Variables defined in a role must start with the role’s name.
Fix
Renamed them to common_….
Lesson
Two roles can then never share a variable by accident.
Shell errors when reading .env
Cause
The token contains a | character.
Fix
Quote the values in .env. The Makefile strips the quotes with sed.
Lesson
Treat secrets as data, not as shell syntax.
Terraform “unsupported argument”
Cause
Option names were guessed instead of read.
Fix
terraform providers schema -json lists the real arguments.
Lesson
Check the schema; do not guess.

No error matches that search.

Daily routine and rebuild

A normal session

terminal
make status      # are the VMs up?
make plan        # does reality match the code?       expect: No changes
make check       # would Ansible change anything?     expect: changed=0
make nodes       # is the cluster healthy?
make deploy      # apply whatever is in k8s/

Rebuild from nothing

The real test of the project: the machines are disposable and the repo is what you keep.

terminal
make destroy     # delete the VMs (check the console for leftover IPs or networks)
make infra       # create 3 VMs, write hosts.yml
make infra       # again, once they are Running: refreshes the IPs
make config      # baseline + k3s on all three
make deploy      # the web UI
Habits that save money and time
  • Machines are billed by the hour while they exist, even when idle. Destroy them when you stop for a while.
  • The state file is local. If you lose it, Terraform forgets the VMs. A team keeps it in shared storage.
  • Only port 22 is open to the internet. The cluster API (6443) and web ports (80/443) stay closed until something is ready to serve, and then open only to your own IP first.
  • Always read the plan before you apply.
